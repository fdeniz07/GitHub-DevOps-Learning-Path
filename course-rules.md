# Course Rules

## Purpose

This document defines the educational standards used throughout the GitHub & DevOps Learning Path repository. Its purpose is to ensure consistency, quality, and a predictable learning experience across all educational materials.

---

# Educational Philosophy

The course follows a project-based learning approach where learners understand concepts first and immediately apply them through practical examples.

Learning is organized around real-world software development workflows rather than isolated theoretical topics.

---

# Learning Principles

The course follows these principles:

- Learn concepts before memorizing commands.
- Every theory section should include practical examples.
- Every notebook should end with hands-on practice.
- Topics should build progressively from beginner to advanced.
- Content should remain technology-focused and vendor-neutral whenever possible.
- Examples should reflect real-world development practices.

---

# Course Structure

The learning path is organized into five major parts:

1. Git Foundations
2. GitHub
3. GitHub Actions
4. CI/CD
5. DevOps

Each part consists of multiple chapters.

---

# Chapter Structure

Every chapter should contain the following educational artifacts when applicable:

- Notebook
- Exercise
- Lab
- Quiz
- Summary

The notebook is the primary learning resource. Other artifacts support and reinforce the notebook.

---

# Notebook Standard

Every notebook should include:

- Title
- Learning Objectives
- Introduction
- Theory
- Practical Examples
- Best Practices
- Common Mistakes
- Chapter Summary
- Next Steps

---

# Exercise Standard

Exercises should:

- Reinforce concepts introduced in the notebook.
- Focus on one learning objective at a time.
- Increase gradually in difficulty.
- Encourage independent problem solving.

---

# Lab Standard

Labs should simulate realistic development scenarios.

A lab may combine concepts from multiple chapters but should clearly state any prerequisites.

Each lab should include:

- Objective
- Requirements
- Step-by-step Tasks
- Expected Outcome

---

# Quiz Standard

Quizzes should evaluate understanding rather than memorization.

Questions may include:

- Multiple Choice
- True / False
- Short Answer
- Practical Scenarios

---

# Summary Standard

Each summary should:

- Review key concepts
- Highlight best practices
- Reference related chapters
- Prepare learners for the next topic

---

# Coding Example Rules

Code examples should:

- Be complete and executable whenever possible.
- Use meaningful names.
- Follow language-specific best practices.
- Avoid unnecessary complexity.
- Include comments only when they improve understanding.

---

# Difficulty Levels

The repository uses three learning levels:

- Beginner
- Intermediate
- Advanced

Difficulty should increase gradually throughout the learning path.

---

# Learning Time

Each chapter should include an estimated completion time.

Suggested ranges:

- Reading: 15–30 minutes
- Examples: 15–30 minutes
- Exercise: 20–40 minutes
- Lab: 30–90 minutes

---

# Navigation Rules

Every educational artifact should provide navigation to related content when available.

Examples include:

- Previous Chapter
- Next Chapter
- Related Exercise
- Related Lab
- Related Quiz

---

# Naming Convention

Files should use descriptive, lowercase names with hyphens.

Examples:

```
01-git-introduction.md
02-git-branches.md
03-github-workflows.md
```

Numbering should reflect the learning order defined in the roadmap.

---

# Content Quality Rules

Educational content should be:

- Accurate
- Clear
- Practical
- Consistent
- Beginner-friendly
- Free from duplicated explanations

Whenever possible, examples should represent real-world development workflows.

---

# Review Checklist

Before publishing any educational content, verify that:

- Learning objectives are defined.
- Examples have been tested.
- Navigation links are correct.
- Grammar and formatting are consistent.
- File naming follows repository conventions.
- Related artifacts are referenced where applicable.
- Markdown renders correctly.

Only reviewed content should be considered complete.
